**Date:** 2026-08-22
**Owner:** ChatGPT / shared with Grok
**Source of truth:** `main` + current production response

## Executive result

The current Vercel production homepage responds HTTP 200 and is served by Vercel/Next.js with RTL Persian metadata and the current neon/gold visual system. The deployment is therefore reachable and rendering.

## Verified

- Production `https://hamnavaz.vercel.app/` returns HTTP 200.
- Security headers are present: HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy.
- Current frontend is Next.js and the production page is prerendered.
- Canonical frontend API client uses `NEXT_PUBLIC_API_URL` / `NEXT_PUBLIC_API_BASE_URL` with `/api` fallback.
- API client supports auth, musician search, matching, collaboration requests, messages, notifications, favorites and ratings.
- Repository contains persistent coordination files: `PROJECT_MEMORY.md`, `DECISIONS.md`, `CHANGELOG.md`, `TODO.md`, `GROK_HANDOFF.md`.
- `main` contains agent skills under `.agents/skills` and GitHub skills under `.github/skills`.

## Integration gaps found

### P0 — Home online section is still static

`frontend/app/page.tsx` defines `onlineMusicians` as a hard-coded array of four people. This conflicts with the product rule that online presence must come from backend state (`last_seen_at` / `is_online`).

Required completion:

- Load real musicians through `/search/musicians`.
- Request `online=true`.
- Render the returned users.
- Keep a graceful empty/loading/error state.
- Preserve the current visual design and four-card desktop layout.

### P0 — Home discovery filters are not mapped to canonical API parameters

Home currently collects city, instrument, skill and style values, but navigates with `city`, `instrument`, `skill`, and `style`. The canonical API client currently models `city_id`, `instrument_id`, `level`, and `online`; backend support for style must be verified before adding it to the API contract.

Required completion:

- Align Home search query with the actual `/search/musicians` contract.
- Do not invent backend parameters.
- Preserve user-selected filters when opening `/musicians`.

### P1 — Musicians filter controls are visually present but not fully wired

The `/musicians` UI currently exposes filter controls, but active filter state is not fully translated into API requests. The `searchMusicians` client already supports `city_id`, `instrument_id`, `level`, and `online`.

Required completion:

- Wire controls to real API parameters.
- Use backend IDs where the API requires IDs.
- Add loading/error/empty states.
- Preserve query-string state on refresh/navigation.

### P1 — Static product showcase data needs explicit classification

Teachers, concerts, music cards and ticket cards on Home are currently presentation data. They must either be connected to real domains/APIs or be explicitly marked as roadmap/demo content. Do not present fabricated production data as live user/event data.

## Architecture guardrails
